## Failure Analysis

The memory recovery check failed significantly in this run:

- Baseline: 12Mi (fresh pod restart — lowest baseline observed)
- Post-deletion (best): 54Mi (at 60s)
- Post-deletion (extended): 77Mi (at 300s — memory *grew* after deletion)
- Threshold: 24Mi (2x baseline)
- **Overshoot: 30Mi above threshold (at 60s), 53Mi above threshold (at 300s)**

### Anomalous behavior: memory increase after deletion

Unlike previous runs where memory decreased over time after dashboard deletion, this run shows perses-operator memory **rising** from 54Mi → 77Mi during the extended wait. Possible explanations:

1. **Delayed reconciliation:** The operator may have been processing deletion finalizers or re-syncing informer caches during the extended wait
2. **Fresh pod with low baseline:** The pod was recently restarted (12Mi baseline vs 20-23Mi in prior runs), and Go runtime heap may have grown as it warmed up
3. **Cluster pressure:** Node ip-10-0-76-17 was at 98% CPU during baseline — overall cluster load was higher than prior runs
