### Key Observations

1. **Post-creation peak depends on starting point:** From a fresh 14Mi baseline, the operator grows to ~105Mi (+91Mi). From a warm 77Mi baseline, it only grows to 126Mi (+49Mi). This shows the Go runtime reuses existing heap allocations rather than growing unbounded.

2. **Recovery is consistent in absolute terms:** Post-deletion memory stabilizes at 44–80Mi regardless of how high the peak was. The residual memory is proportional to the warm baseline, not the peak.

3. **No unbounded growth across runs:** Run 3 started at 77Mi (warm from Run 2's post-deletion state of 50Mi + time for GC settling). After 600 more dashboards and deletion, it landed at 80Mi — essentially the same level. This confirms no cumulative leak across cycles.

4. **Run 2 failure is a false positive:** The 14Mi fresh-pod baseline produces a 28Mi threshold that's impossible to meet after processing 600 dashboards. The absolute post-deletion memory (50Mi) is healthy and consistent with other runs.

5. **Perses server memory is stable:** Consistently peaks at 72–74Mi under load, recovers to 58–63Mi. No growth across runs.

### Recommendation

The 2x-baseline threshold is effective for warm pods (baseline >= 40Mi) but produces false failures for fresh pods. Consider using `max(2x baseline, 60Mi)` as the threshold to account for Go runtime heap retention after first major allocation.
